# Cross-Team Coordination Protocol｜A/B/C 跨团队协作协议

## 1. 目的
让 A/B/C 并行推进，不因某个成员的资产、技术或设计问题停摆；同时保证接口一致、成果可复用、工程可恢复。

## 2. 责任边界
- A：公共接口、列车 Hub、项目/资产交接验证、主集成。
- B：书桌站自己的场景、资产和玩法。
- C：失重花园自己的场景、资产和玩法。
- 总设计师：核心设计决策、关键 Tripo 生成、视觉/玩法 Review 和最终验收。

每个场景和二进制文件只有一个主要写入者。跨团队协作不等于多人同时编辑同一工程文件。

## 3. 必须主动交换的信息

### A → B/C
- 玩家尺度和出生点约定。
- Entry/Exit Anchor 格式。
- 已验证的 GLB/WPRE 导入和交接结果。
- 列车返回/下一站连接方案。
- 集成版本的依赖与限制。

### B/C → A
- 世界入口、出口、朝向和安全落脚区。
- 当前白盒/稳定快照及 Commit。
- 场景依赖、资产格式和导入注意事项。
- 玩法状态和离开世界的时机。
- 尚未解决的集成风险。

### B ↔ C
- 造世界编辑器技巧、AI 地形/资产导入经验。
- Blender 修复、材质、碰撞和性能经验。
- 对方世界的可读性和玩法差异 Review。
- 失败复现和可复用降级方案。

## 4. 交接格式
每次交接用简短消息，并在自己的 `reports/day-XX/OWNER/HANDOFF.md` 留档：
- 交付内容：
- 分支 / Commit：
- 文件或资源路径：
- 当前状态：可用 / 临时占位 / 待验证 / 不可用
- 如何复现或导入：
- 依赖：
- 已知问题：
- 希望接收方做什么：

不要只发“做好了”。必须给出 Commit、文件和证据。

## 5. 阻塞局部化
1. 说明具体被阻塞的子任务和影响范围。
2. 进行一次 20–30 分钟最小验证。
3. 记录错误、版本、复现步骤和证据。
4. 提出一个最低成本降级方案。
5. 向具体依赖方发出明确请求（需要什么、格式、截止点）。
6. 冻结受影响子任务，继续其他独立任务。
7. 依赖到达后恢复原任务，验证是否可以撤销临时方案。

禁止把 BLOCKED 扩大成整个成员或整个项目停止。

## 6. Git 协作与共享
- A/B/C 各自在自己的 feature 分支提交。
- 每个可审阅阶段成果尽早 push，并开 PR 或在团队群分享分支/Commit。
- 不要等待 PR 合并才让其他成员开始参考；可以基于明确的 Commit 做临时验证。
- 任何人不得直接向 main 推送。
- A 负责公共接口和集成 PR；总设计师负责设计 Review。
- 二进制场景/模型冲突不做文本合并；由文件 Owner 选定版本并保留回滚点。
- 不把编辑器缓存、临时下载、凭证和未核验的大体积文件提交到仓库。

## 7. 每日协作节奏
- Kickoff：每人发布今日目标、可并行工作和需要的依赖。
- Midday：更新阻塞和接口变化；阻塞任务局部降级。
- Handoff：至少一次跨团队成果交换。
- Daily Review：提交真实证据和次日计划。
- Gate：总设计师/指定 Review 角色决定 APPROVE / REVISE / REJECT / BLOCKED。

## 8. 变更规则
若变更会影响其他世界的入口出口、玩家尺度、核心玩法、关键资产或集成方案，必须先发出变更提案并通知受影响 Owner。非破坏性的局部优化由世界 Owner 自主决定并记录即可。
