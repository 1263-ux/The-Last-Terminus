## 1. 本轮解决的三个真实问题

Day 1 结束时白盒"导入了但看不见"。本轮把它查清并修好了，三处都是**实测坑**，写下来避免团队重复踩。

### 1.1 GLB 缺少 NORMAL → 物体只投影、不显示 ★ 最贵的坑

| 项 | 内容 |
|---|---|
| **症状** | 白盒对象在场景树里存在、有正确位置、**投射了正确的阴影**，但相机里完全看不见表面 |
| **误判过程** | 先后怀疑：地形遮挡 → 物体在原点而出生点在 148 m 外 → 相机朝向反了 → 被地形埋住。全部排除后才发现是法线 |
| **根因** | `tools/make_whitebox.py` 早期版本写出的 GLB 只有 `POSITION + COLOR_0 + 索引`，**没有 `NORMAL`**。引擎的 shadow pass 只需要深度，所以阴影照画；但主 pass 需要法线做光照，缺失时表面不被绘制 |
| **修复** | 在 `write_glb()` 中按面法线累加求平滑顶点法线，写入 `NORMAL` accessor |
| **验证** | 修复后同一批几何体立刻可渲染（`evidence/day-01/09~12`） |

> **给 A/C 的结论：** 只要几何体"有阴影、没表面"，先查 `NORMAL`，不要去调相机和坐标。
> 这条对 C 的 AI 地形/程序化资产同样适用。

### 1.2 出生点与相机朝向（实测，结论修正过一次）

| 项 | 实测值 |
|---|---|
| 出生点 | `(119.741669, 80.0, 88.64061)`，`rot = (0,0,0,1)` 单位四元数 |
| 出生点节点 | `nodeName=出生点`，`tag=BornPoint`，`physicsColliderData=null` |
| 相机对象名 | `TPCameraAvatar` |
| 相机位置 | **(119.703, 78.921, 82.489)** |
| 相机前向 | **(0.0724, −0.3090, 0.9483)** → 朝 **+Z**，俯角约 18° |
| FOV / near / far | 45 / 0.05 / 1000 |

**这两个数值解释了本轮遇到的一切怪现象：**

1. **前向是 +Z**：所以"把道具放 −Z"必然在身后 → 画面空白。我先前两次二分法得出相反结论，**都是错的**。
2. **相机 y = 78.921，比玩家脚下（y = 80.0）低 1.08 m**：第三人称相机在身后**且低于**玩家。因此
   **任何顶面平齐玩家脚底的整块地面板，都会把相机包在板体下方，直接挡死整个视野。**
   这是"有影子没表面"的第二个真正原因（第一个是缺 `NORMAL`）。
3. **俯角 18°**：在 26 m 处视线中心已降到 y ≈ 78.9 − 0.309×26 ≈ **70.9**。
   **凡是放在 y=80 地面上的道具，都落在画面顶部之外**，除非贴近玩家。

### 1.2.1 怎么打通 lua 自动化（可直接复用）

`douyin-world runtime lua eval` 必须选 `--script` / `--binding` / `--global` 之一。
`--global` 下**没有** `UnityEngine` 全局，但有 **`CS`**；并且：

- `cams[0]` / `cams[1]` **都是 nil**；正确写法是 **`cams:get_Item(0)`**
- `GetComponent(CS.UnityEngine.Camera)` 报 `invalid arguments`；必须先用
  **`typeof(CS.UnityEngine.Camera)`** 取 Type 再传入
- `FindObjectsOfType` 在这条桥上不可用，改用 `FindGameObjectsWithTag`

脚本留在 `lua/get_cam.lua`，是本轮最有价值的工具之一（A/C 都能用它测自己世界的视线与尺度）。

### 1.2.2 一条走通的摆位公式

```
按相机实测参数反推道具应放的高度：
  y = camY − tan(pitch) × d      d = 道具到相机的水平距离
本轮实测 pitch ≈ 18°、camY ≈ 78.9：
  d = 26 m  →  y ≈ 70.9    ← 道具应放约 y=71，而不是 y=80
```

**这就是为什么把布局整体压到 y=72 之后，书本与台灯立刻出现在玩家视角里**
（证据 `16-walk-props-visible.jpg`）。这条公式应当成为 Day 2 摆位的标准做法。

### 1.3 桌面几何尺寸与玩家的关系

早期桌面是 40×30 m 的单块板，放置后**玩家站在板内部**，相机被板体包住 → 什么也看不见。
修复：把桌面重做成"近岸板 + 10 m 裂口 + 对岸板"，并把锚点设在让玩家站在近岸板**上表面**。

```
局部坐标（WB_DESK.glb 实测 bbox）
  x: -14 .. +14
  y:   0 .. 0.6
  z:  -6 .. +44
  近岸板: z -6..22      ← 玩家 z=0 站在这里
  裂口:   z 22..32      ← 10 m 宽，正前方
  对岸板: z 32..44      ← 小镇/目标
```

## 3. 规模与尺度复测

| 物件 | 世界尺寸 | 相对玩家(1.7 m) |
|---|---|---|
| 桌面（含裂口） | 28 × 0.6 × 50 m | — |
| 裂口宽度 | 正前方 10 m，z 22–32 | 5.9× |
| 巨书 A | 9 × 7 × 6 m | 4.1×(高) |
| 巨书 B | 7.5 × 5.6 × 5 m | 3.3×(高) |
| 木尺 | 2.6 × 0.56 × **30** m | 17.6×(长) |
| 铅笔盒 | 14 × 2.95 × 9 m | 1.7×(高) |
| 台灯 | 3.8 × 11.3 × 2.6 m | 6.6×(高) |
| 马克杯 | 9 × 6.5 × 8 m | 3.8×(高) |

**一个必须记录的结构性事实：** 尺子 30 m 长、裂口 10 m 宽 → **尺子必然悬空 20 m**。
靠"拖动尺子对准"在物理上不成立，除非只允许它的中段跨在裂口上（视觉上像尺子被斜放卡住）。
这进一步支持 `BLOCKERS.md` B-03 的判断：**尺子桥必须用锚点/预设状态实现，自由摆放不可行**。
或者——把尺子缩短到 12 m（仍是 7× 玩家身高，识别度不受影响）。**这是本轮提出的一个具体修正建议，见 §5。**

## 6. 工具与可复现性

本轮所有几何由 `tools/make_whitebox.py` 生成（纯 numpy，无 Blender、无第三方库），
放置脚本 `tools/place_whitebox.ps1`。清场/重摆的命令序列见 `EVIDENCE.md` §3。

**关键 CLI 经验（已写入 HANDOFF 给 A/C）：**
- 负坐标/负节点 ID 必须用 `=` 形式：`--position=-13,0,-6`、`--object=-12562`
- `scene remove` 只接受**位置参数**的形式（`scene remove -667818639`），传 `--args` 静默失败
- `scene import` 报"超时"时**多数实际已 committed**；用 `scene operation <requestId>` 核实，不要换新 ID 重试（会重复实例）
- 运行中改场景 → 之后 `runtime status` 会长期卡 `loading`。稳定节奏：`stop → 改 → save → start → 立刻连续截图`
- 编辑器卡死时用 `instance stop` + `instance start --project <路径> --mode foreground` 可以干净恢复（本轮用过 3 次）
