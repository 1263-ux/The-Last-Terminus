`SPATIAL-PROPOSALS.md` 推荐的是 **方案 C「反向生长」**（三方案对比 C 20 / B 19 / A 16）。但当时场景里的白盒实际上是**线性拓扑**——温室在入口**上方**。

## 2. 方案 C 的空间结构（已实现）

### 2.1 高度分层

| 层 | 高度 | 内容 |
|---|---|---|
| 花冠层 | y = 26 | 花冠观景台（终点，最高点） |
| 入口层 | y = 20 | 入口浮岛，玩家出生点 |
| 温室屋顶 | y = 16 | **可走面**（倒悬后原本的地面朝上） |
| 温室穹顶 | y = 8 | 尖端朝下 |
| 根系层 | y = 0 | 岛底岩锥与远景 |

**关键：目标在玩家下方，不是前方也不是上方。**

### 2.2 路线

```
出生点 (0, 20, -13)
  ↓ 朝 +Z 走
入口岛 (0, 20, -10)
  ↓ 正面是断桥（栏杆封住，过不去）
断桥断口 (0, 19.9, -3.6)   ← 直线路径在这里失效
  ↓ 转向 +X 侧
根系下坡 17 级 (x=4.2, y 20→16, z -4→10)   ← "原来这里也能走"
  ↓
温室屋顶 (0, 16, 8)   ← 玩家站在一栋倒着盖的房子房顶上
  ↓ 空中平台链 6 级 (y 17.2 → 26)
花冠观景台 (0, 26, 28.5)
```

### 2.3 断桥的作用（设计意图）

断桥不是装饰，是**「直线路径不成立」的实体证据**：

- 桥两侧有 0.9 m 栏杆，明确传达"这里过不去"
- 玩家在断口会本能地研究它（参考研究：允许 20–30 s）
- 真正的路在侧后方 +X 侧，需要转身才能看到

**这就是"原来这里也能走"的结构性来源**——不是藏了一条支路，而是玩家发现自己一直在错误的参照系里。

## 4. 本轮修掉的两个真实缺陷

### 缺陷 1｜下坡台阶让人掉下去

第一版下坡用了 `x = 2.2 + sin(t*π)*1.2` 的外弧，想让它"看起来不像直桥"。结果：

- 台阶横向摆动，玩家走直线会从侧面走出去
- 实测：`y` 从 70 直接掉到 19.22，然后被世界边界清理弹回出生点

**修正**：改成**笔直沿 +Z、全程同宽 3.2 m、每级降 0.25 m**。重建后走通。

**这条与 T-05 是同一个教训的第二次出现**：可走面必须是可预测的，任何"为了好看"的几何变化都会变成玩家的坠落。

### 缺陷 2｜下坡起点与断桥重叠

第一版下坡放在 `x=0`，正好压在断桥的延长线上——那样断桥就不再是阻碍了，玩家可以顺着台阶直接下去。

**修正**：下坡移到 `x=4.2`（+X 侧），断桥保持在 `x=0`。现在断桥是真障碍，真路在侧后方。

### 5.1 屋顶 → 花冠：已修复并实测走通

**原缺陷**：屋顶 y=16.0，首块空中平台 y=17.2，高差 **1.2 m**，远超可跨越台阶上限（当时按 0.30 m 估，T-17 实测为 0.45 m，结论不变）。且后续 6 块平台每块抬 1.76 m——那是**跳跃**段，而本世界按 `TASK.md` 不做跳跃玩法。整条"屋顶→花冠"实际是不可通行的。

**修复**：改成 **34 级连续小台阶**，每级抬 0.294 m、间距 0.412 m、深度 1.5 m（相邻重叠），每 5 级做一块 3.6 m 宽的休息平台。0.294 m 在 T-17 实测的 0.45 m 上限之内。

```
y 16.0 → 26.0（抬 10 m），z 10.0 → 24.0
每级 dy = 0.294 m，dz = 0.412 m
```

**实测**（真实 `MoveContinuously`）：

```
从温室屋顶落下： (120, 66.30, 123)
连续上行后：     (120, 76.00, 145.40)
```

`y` 单调上升 **9.7 m**，`z` 前进 22.4 m，**全程踩在台阶上，无坠落、无卡死**。路线现在从出生点到花冠台是**完整可走的**。

### 5.2 观景台护栏：已修（但验收方法本身出了个坑）

**原缺陷**：观景台三面 1.0 m 护栏太高，玩家站上去主要看到护栏，看不到来路（违反参考研究硬结论 3）。

**修复**：
- 平台从 `z=28.5` 前移到 `z=26.5`（玩家接近台阶顶端时就已在台缘）
- 护栏从 1.0 m 降到 0.55 m（低于第三人称相机高度）
- 朝 -Z（来路）那一面**完全开口**
- 加一块 3.2×1.6 m 的浅色铺面，暗示"站在这里往回看"

### 5.3 一个必须记录的验收方法坑

修完之后我用 `Teleport` 把玩家放到观景台上截图，得到的是**一片空白的地面**，看起来"观景台不存在"。

诊断结果：

```
playerY = 78.31
groundY = 0        ← 射线打到的地面高度是 0
collider = null
```

**玩家悬在半空。`actor:Teleport` 不触发重力沉降**，它把角色放在指定坐标后停在那里，不会下落去贴合地面。所以我之前几轮"传送到平台上截图"得到的构图，有一部分是**角色悬空**状态下拍的，不能作为"这里能站"的证据。

**正确做法**（本轮改用）：

```
从温室屋顶 (120, 68, 123) 落下并等待 50 帧 → 确认真实着地
再用 MoveContinuously 沿 +Z 真实行走 → 记录逐帧 y/z
```

**真实行走结果**：

```
start  y=66.30, z=123.0   （温室屋顶，真实着地）
end    y=74.83, z=136.9   （台阶中上段）
```

`y` 单调上升 8.53 m，`z` 前进 13.9 m，全程实走，无坠落、无卡死。截图 `33-planC-stairs-arrival.png` 是从这个真实状态拍的：玩家站在台阶上，前方是观景台与其 0.55 m 护栏。

**这条要写进交接**：`Teleport` 只用于"把玩家放到某个位置"，**不能用来证明"那里能站"**。任何"能不能站/能不能走"的证据必须来自真实落地 + 真实行走。

### 5.4 射线检测不可靠（仍然失败的一项）

本轮多次尝试用 `Physics.Raycast` 向下找地面高度，在合并后的白盒上**持续返回 0 或打空**，而玩家实际能站在 y≈66–75。原因是几何被 `__optimized_merged_material_N` 重新合并后，射线的碰撞层/包围体与视觉网格不一致。

**结论**：判断"有没有可站面"不要靠 raycast，靠**真实角色落地**。已记入交接。

### 5.5 温室"倒着"的可读性：已修复（轮 3）

这是方案 C 最大的单一风险。参考研究 R-01 明确预警：**倒置必须靠结构传达，不能靠错觉或贴图**（Monument Valley 的签名手法在自由视角下整体不可用）。

#### 根因一：屋顶根本没长在温室上

读源码发现一个真实的几何错误：

```
greenCenter.y = 12.0   （温室组原点）
温室本体（翻转后）： y = 7.0 .. 12.0
穹顶（朝下）：       y = 3.0 .. 7.0
屋顶可走面：         y = 16.0
```

**屋顶悬在温室上方 4 m，与温室完全脱开。** 玩家站在一块孤立圆盘上，自然读不出"这是房顶"。

修正：`greenCenter.y` 从 `12.0` 抬到 `16.0`，让翻转后本体的顶面正好等于屋顶可走面。修正后：

```
屋顶可走面   y = 16.0
温室本体     y = 11.0 .. 16.0
穹顶（朝下） y =  7.0 .. 11.0
```

#### 根因二：只有"绕 X 翻转 180°"，没有任何结构证据

玻璃是透明的，翻转前后轮廓几乎一样。按参考研究的结论，补了三条**只在"倒着"时才在物理上成立**的结构：

| # | 线索 | 为什么它只能属于倒置建筑 |
|---|---|---|
| 1 | 屋顶排水口的檐口**朝上张开**（上宽下窄） | 正常檐口向下兜水 |
| 2 | 六根立柱的**底座法兰与螺栓露在屋顶上** | 正常柱子埋在地里、法兰朝下 |
| 3 | 穹顶下段的**采光窗朝向地面** | 正常温室天窗朝天 |

#### 实拍确认（截图 `35` / `37`）

玩家真实落在屋顶中心后：三个朝上张开的檐口、屋顶天窗、法兰与螺栓都在近景清晰可见。倒置不再依赖"看出来是翻转的"，而是由物理结构直接给出。

#### 顺带修掉的构图问题

加完线索后发现 **34 级台阶在屋顶正中叠成一根蓝色柱子**（截图 `35`），把"站在房顶上"的体验完全遮住。把台阶链整体移到 `x=5.0`（与下坡段 `x=4.2` 对齐），屋顶中心留空（截图 `36` / `37`）。同时在台阶顶端与观景台之间补了 4 块等高平板，把玩家横向带回中轴，避免留下 5 m 横向缺口。

### 5.6 GLB 导出会镜像 X 轴（新发现，高优先级）

移完台阶后按源码坐标 `x=5.0 → 世界 125` 去落点，玩家**直接掉下云海**。查运行时包围盒发现台阶实际在 `x≈115`。

对照实验：

| 尝试落点 | 结果 |
|---|---|
| `x = 115.8`（= 120 − 4.2） | 落在下坡台阶上，`y = 67.50` ✅ |
| `x = 124.2`（= 120 + 4.2） | 掉下去，`y = −11.15` ❌ |

**结论：Three.js 源码里的 `+X` 在导出 GLB 后变成运行时的 `−X`。** 这与 R-08 同源——WPrefab 的 GLB 烘焙会重写变换，不能用源码坐标直接推算世界坐标。

用镜像后的坐标重新实测上行台阶（截图 `38`）：

```
落点 (115.0, 66.91, 125.6)  ← 第 3 级上行台阶顶面 = 50 + 16.9 = 66.9 ✅
实走 y 66.91 → 70.71（+3.80 m），z 125.6 → 130.8，x 稳定 115
全程单调爬升、踩台阶、无坠落
```

**给 A/B 的交接要点**：任何依赖源码坐标的外部脚本（触发器、传送点、集成锚点）都必须以**运行时实测坐标**为准，或者在导入后统一做一次 X 取反。绝不能拿 Three.js 源码里的 x 直接当世界坐标用。
