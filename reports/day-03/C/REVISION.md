### 6.4 运行时清除残留实例的有效方法（重要，解除测量污染）

上两轮一直卡在"场景里有多个重叠白盒"，`scene remove` 需要精确 root id 而 CLI
没有枚举入口。本轮找到**可行的运行时解法**：

```js
const root = CS.UnityEngine.GameObject.Find('previewGameRoot');
const list = [];
for (let i = 0; i < root.transform.childCount; i++) {
  const c = root.transform.GetChild(i);
  if (c.name === 'garden-whitebox') list.push(c.gameObject);
}
// 保留第一个，销毁其余
for (let i = 1; i < list.length; i++) {
  CS.UnityEngine.Object.DestroyImmediate(list[i]);
}
```

实测一次清掉 2 个，清完后场景只剩 `Env / 地图 / 出生点 / garden-whitebox ×1`。

**但这是运行时修改，不写盘。** `scene save` 会再次把重复实例写回，
所以它只能用于**当次验证**，不能根治。根治仍需 GUI 手动删除或官方枚举 API。

**这条对本轮验证很关键**——之前所有"传送能站但走路被挡""相机读数自相矛盾"
的怪现象，根因都是多实例叠加。

### 6.5 修复：出生点标记物挡住了主路线（严重，玩家走不出入口岛）

**轮 20 实测发现。** 从入口岛沿 +Z 走，玩家在 `z=101.6` 被**硬挡住**，
但传送进同一位置又能站住（`y=70`）——说明不是缺地面，是**有东西挡路**。

扫 `z∈[94,106]` 的渲染体，找到元凶：

```
z=102.0, y=70.3, 尺寸 0.5 × 0.5 × 0.5    ← SpawnMarker
z=105.2, y=69.5, 尺寸 12  × 1.1 × 12.4   ← 入口岛面（正常）
```

源文件里是：

```js
addBox(entryZone, 'SpawnMarker', 0.5, 0.5, 0.5, 0, 20.25, -13);
```

它本来只是标"出生点在哪"的**视觉小方块**，却被放在**主路线正中央**，
且 0.5 m 的高度远超可跨越台阶上限的一半，**实际把玩家挡死了**。

这同时违反 `ASSET-CARDS §0.2` 第 1 条「装饰几何不得干扰可走面」，
也正好撞上设计总监 §2 反复强调的那条：**不要假设几何与行走的关系**——
这里是反向案例：小到不该被注意的装饰，反而成了硬阻挡。

**修复**：移到路线左侧 `x=-3.2`，高度压到 `0.12 m`（低于可感知阻挡），
只作视觉标记，不参与行走判断。

```js
addBox(entryZone, 'SpawnMarker', 0.5, 0.12, 0.5, -3.2, 20.06, -13);
```

**修复后实测**（白盒导入到 `(200,50,200)` 隔离验证）：

```
修复前：从 z=187 走 → 卡在 z=189.6（对应原世界 z=101.6）
修复后：z=187 → 191.4 → 194.4（穿过原阻挡点，最后停在入口岛真实边缘）
```

停下的 `z=194.4` 对应原世界 `z≈109`，正是**断桥断口**的位置——
说明修复后玩家能正常走到断口被阻断，**断桥设计没有被破坏**。
证据：`evidence/day-03/C/06-walk-past-fixed-blocker.png`

### 6.7 新发现并修复：复位点是硬编码世界坐标（严重，影响 WPrefab 可复用性）

清理后把白盒**导入到另一个世界位置 `(200,50,200)`** 做隔离测试时暴露：

```
玩家被云垫接住后复位到 (120, 70, 107)
                              ↑ 这是原世界位置，不是新实例的 (200,70,192)
```

原因：`fall_respawn.lua` 把 `RespawnX/Y/Z` 直接当**世界坐标**用，
WPrefab 换个位置就复位到空气里（那正好是原来白盒的位置）。

**这会让 WPrefab 完全不可复用**——A 若要把它集成到列车枢纽，玩家一掉就被
传送到一个空坐标。属于必须在交接前修掉的缺陷。

**修复**：参数改为**局部坐标**，运行时沿父链找到 `garden-whitebox` 根，
用 `host:TransformPoint(local)` 换算成世界坐标：

```lua
local wp = host:TransformPoint(CS.UnityEngine.Vector3(lx, ly, lz))
```

**修复后实测**（白盒放在 `(200,50,200)`，局部复位点 `(0, 21, -8)`）：

```
BEFORE  : 0:none
掉入云垫: (200, 54, 212)
复位到  : (200, 70, 192)   ← 200+0, 50+20, 200-8，正确
AFTER   : 1:respawned
```

证据：`evidence/day-03/C/03-respawn-local-coords.png`

> **方法论收获**：这个缺陷是靠"把 WPrefab 换到不同世界位置再测"发现的。
> 之前一直在 `(120,50,115)` 测试，硬编码坐标恰好正确，问题被掩盖。
> **凡是写死世界坐标的脚本，都必须换一个位置复测才能验出来。**

### 6.8 `DouyinCameraService` 存在且可用（重要，纠正旧结论）

编辑器暴露 `CS.DouyinCameraService`，运行时可用：

| 方法 | 实测 |
|---|---|
| `SetYaw(180)` | forward 从 `(0,+0.95)` → `(0,−0.95)`，`GetYaw` 读回 180 ✅ |
| `SetPitch(28)` | 实际改变俯仰 |
| `GetYaw/GetPitch` | 可读 |

**纠正 R-08**：我此前写"相机不跟随角色朝向、无法控制"——不准确。
准确说法：相机**不跟 `actor.rotation`**，但 `DouyinCameraService` 提供**程序化**设置入口，
且相机跟随**移动方向**。这不改变 §4.1 的裁决（仍不该用它做强制定向），
但它是**调试与验收**的有力工具（我这轮的 pitch 扫描就靠它）。

### 6.10 `scripts.unbind` 必须用位置数组


设计总监的 §4.1 撤回了"同框"要求，我据此删掉了上一轮做的脚本强制相机；
新口径第一条（到达时下一个目标可见）**实测通过**，第二条（3 秒内回头认出来路）

> 本轮最值得记住的两条方法论：
> 1. **硬编码世界坐标的问题，只有把 WPrefab 换到另一个世界位置测试才会暴露。**
> 2. **"能传送进去站住"不等于"能走过去"**——必须有连续行走测试，
>    否则路线中央的装饰方块会被完全漏掉。
