# 分层配色审计（garden_layer_tint，Day 4）

> 目的：确认 `garden_layer_tint.lua` 现在到底把三层涂成了什么，是否只是"颜色少"还是"涂错"。
> 数据来源：runtime `59ded821` 实读（脚本宿主 `Model` 原点 `y=50.00`，9 个合并渲染器）。

## 2. 结论：不是"少几种颜色"，是**涂错层**

| 问题 | 证据 |
|---|---|
| **入口岛被涂成屋顶色** | `m0`（y 69–70.07，就是玩家出生/站立的入口面）localY=19.54 > 18.5 → RoofColor 青蓝，而不是 EntryColor 薄荷绿 |
| **温室屋顶被涂成根系色** | `m6`（y 65.5–66，屋顶可走面）localY=15.75 < 18.5 → RootColor 绿，与根系同色 |
| **楼梯/屋顶/花冠共用一色** | `m7` 一个网格跨 y 66–79.2，被整体涂成花冠紫 |
| **围栏/框架被涂成根绿** | `m3` localY=17.25 → RootColor |
| **颜色档只有 3 个** | 实读去重后 3 色；Day 3 用原生材质时是 9 色 |

根因还是 Day 3 §6.0b 那条：**合并网格后 `renderer.bounds` 不能代表单层**（`m7` 跨 13 m、`m1` 跨 34 m），
任何"按 bounds.center.y 分层"的脚本都不可能对。

→ 这不是"美术偏好"，是**三层空间辨识度被涂反**（玩家看到的入口是蓝色、温室屋顶是绿色）。

### 2.1 画面上就是这么难读（路线实拍）

`reports/day-04/C/route-walkthrough.png` 是沿主路线 7 个实测点拍的图：
入口甲板、断桥、根系下坡、温室屋顶、台阶、台阶顶、花冠北条带——
**七个点的可走面几乎全是同一种深蓝**，只有围栏/框架是绿，看不出"根系绿 / 温室青蓝 / 花冠紫"的三层区别。

这就是要修的理由：玩家靠颜色区分"自己在哪一层"的信息现在几乎为零。

## 3. 处置建议（按优先级）

1. **解绑 `garden_layer_tint.lua`，用 GLB 原生材质**（Day 3 §6.0b 已验证 9 色、三层可读）。需要 GUI 会话；
   注意：脚本源码**内嵌在 `scene.data` 的 `runtimeScripts` 里**，只改工程里的 `.lua` 文件不会影响场景。
2. 若必须保留脚本：改成**按渲染器名 / 材质名映射**（`__optimized_merged_material_N` 与语义层一一对照，
   本文件 §1 的表就是现成映射），不再用 bounds。
3. 任何改法都必须重拍对照图：入口岛（应是薄荷绿）、温室屋顶（青蓝）、花冠（紫），三层一眼可分。

## 4. 为什么不能"运行时恢复原生色"（本轮实测）

试过读 `renderer.sharedMaterial` 与 `renderer.material` 对比，想从 shared 材质拿回 GLB 原生颜色：

```
SpawnMarker | shared=#51,107,140 | instance=#51,107,140 | SAME
m0 | shared=#51,107,140 | instance=#51,107,140 | SAME
m1 | shared=#71,122,76  | instance=#71,122,76  | SAME
m3 | shared=#71,122,76  | instance=#71,122,76  | SAME
m4 | shared=#51,107,140 | instance=#51,107,140 | SAME
m5 | shared=#71,122,76  | instance=#71,122,76  | SAME
m6 | shared=#71,122,76  | instance=#71,122,76  | SAME
m7 | shared=#122,92,158 | instance=#122,92,158 | SAME
m8 | shared=#71,122,76  | instance=#71,122,76  | SAME
```

- 合并后的材质**本身已经是 `(Instance)`**，shared 与 instance 指向同一个被改写过的实例；
- 结论：**原生色在运行时已经拿不回来了**，只能通过"解绑脚本 + 重新导入/重建"恢复；
- 这也说明：想在截图里"预览解绑后的样子"，必须真解绑重开，不能靠运行时改色伪造（本轮不做假证据）。
